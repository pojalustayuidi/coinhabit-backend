# Решения Android MVP

- Новая регистрация возвращает текущий Android `AuthResponse(token,user)`; подтверждение
  email не является условием выдачи/проверки JWT. `emailVerified` отражает только реальное
  подтверждение. Старым аккаунтам не выставляется фиктивный true; null трактуется как false.
- Настоящий гость — отдельная запись users с новым UUID, is_guest=true и SQL NULL email и
  password_hash. JWT имеет ту же роль USER и claim userId, поэтому привычки, события RabbitMQ,
  накопления и цели используют прежние механизмы владения.
- Новый JWT subject — UUID. Auth принимает прежние JWT с subject=email только при совпадении
  и UUID, и текущего email. Auth principal теперь UUID. Habits/savings не зависят от email;
  все три сервиса проверяют подпись, exp и корректность UUID. JWT без exp отклоняется.
- Upgrade требует действующий Bearer гостя и блокирует строку users на время транзакции.
  UUID не меняется; никакого копирования данных между БД. Уникальность нормализованного email
  обеспечивается PostgreSQL, включая гонки регистрации. Занятый email и повторный upgrade —
  409, автоматического объединения аккаунтов нет.
- Регистрация/вход/upgrade не обращаются к SMTP. Только явный запрос создаёт одноразовый
  24-часовой token с SHA-256 в БД и отправляет письмо после commit. Ошибка доставки логируется
  без токена/адреса и не ломает сессию. Общий ответ не гарантирует доставку. Новый запрос
  аннулирует предыдущие ссылки, повторное использование/истечение — 400. Существующий
  rate limiter (2 минуты / 5 за сутки / ограниченная память) сохранён.
- Обычная сессия — 24 часа, гостевая — 7 суток. Значения конфигурируются в пределах 1 минуты
  — 7 суток. Семь суток дают время попробовать приложение и зарегистрироваться; бессрочной
  анонимной авторизации нет. Refresh/recovery токенов в существующей архитектуре нет, они
  здесь не добавлены. Потеря или истечение единственного гостевого JWT означает невозможность
  восстановить доступ: email и пароля нет. Клиент должен явно сообщить это до начала работы.
- После upgrade старый гостевой JWT сохраняет доступ до исходного exp (в том числе в
  stateless habits/savings); клиент заменяет его новым. Выход удаляет токен только на
  устройстве. Немедленной серверной блокировки JWT нет; не считать upgrade механизмом
  отзыва украденного токена. Использовать защищённое хранилище клиента и HTTPS.
- Создание гостей: максимум 10 на socket-IP за час и 1000 суммарно за час на экземпляр auth.
  Ограничитель потокобезопасен и ограничен по памяти; отклонение — 429. X-Forwarded-For
  намеренно не доверяем, автоматическая обработка forwarded headers явно отключена.
  За reverse proxy все клиенты могут разделять один лимит. Перед публичным или многорепличным
  запуском нужен общий лимит на доверенном gateway; перезапуск процесса сбрасывает счётчики.
  Старые анонимные записи автоматически не удаляются: удаление потребовало бы согласованного
  удаления данных в трёх сервисах. Это ограничение MVP, не обещание контроля общего роста БД.
- Auth переходит с Hibernate update на Flyway baseline 0 + V1 и validate; миграция сохраняет
  данные и отказывается объединять конфликтующие email. Habit/savings schema management
  и финансовые расчёты не меняются.
- Полный Compose добавлен поверх PostgreSQL/RabbitMQ; init job безопасно создаёт отсутствующую
  savings_db на старом volume. SMTP/Mailpit опционален. Секреты только через окружение.

- springdoc в habits выровнен с auth до 3.1.0: прежняя 2.8.4 предназначена для Boot 3,
  тогда как репозиторий использует Boot 4.1. [Матрица совместимости](https://springdoc.org/faq.html).
